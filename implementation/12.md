# Section 12 — SQLite Database Implementation

> **Objective:** Design and implement a normalized relational database that serves as the **single source of truth** for the entire application.

---

# Overview

SQLite is the foundation of the project.

Every component—including the scraper, analytics engine, embedding pipeline, AI agents, and dashboard—depends on this database.

**Important Principle**

```
LeetCode

↓

SQLite

↓

Everything Else
```

SQLite is the authoritative data source.

ChromaDB, JSON files, charts, and AI summaries are all derived from SQLite.

---

# 12.1 Database Responsibilities

The database stores:

- Question metadata
- User submissions
- Tags
- Analytics
- AI-generated summaries
- Synchronization state

It does **not** store embeddings. Embeddings belong in ChromaDB.

# 12.15 Transactions

Whenever multiple tables are updated:

```
Insert Submission

↓

Insert Tags

↓

Update Analytics

↓

Commit
```

If one operation fails:

```

```

This prevents inconsistent data.

---

# 12.16 Validation Rules

Before inserting data:

- Question title cannot be empty.
- Difficulty must be Easy, Medium, or Hard.
- Submission ID must be unique.
- Foreign keys must exist.
- Duplicate tags are not allowed.

Validation should occur before database writes.

---

# 12.17 Pagination

Large datasets should never be returned entirely.

Instead:

```
SELECT

↓

LIMIT

↓

OFFSET
```

Example:

```
Page Size = 50
```

Useful for dashboards and APIs.

---

# 12.18 Query Optimization

Common optimization techniques:

- Select only required columns.
- Use indexes.
- Batch inserts.
- Avoid unnecessary joins.
- Cache expensive analytics.

These practices keep the application responsive as the number of submissions grows.

---

# 12.19 Backup Strategy

Regularly back up:

```
SQLite Database

↓

Compressed Backup

↓

GitHub Release

or

Cloud Storage
```

Since ChromaDB can be regenerated, SQLite backups are the highest priority.

---

# 12.20 Database Lifecycle

```
Scraper

↓

SQLite Updated

↓

Analytics Updated

↓

Embedding Generated

↓

ChromaDB Updated

↓

Dashboard Updated
```

SQLite remains the center of every workflow.

---

# Best Practices

- Normalize tables.
- Use foreign keys.
- Add indexes for frequently queried columns.
- Keep SQL inside repositories.
- Use transactions for multi-step operations.
- Cache AI-generated content when appropriate.
- Treat SQLite as immutable history—never delete submissions unless necessary.

---

- Efficient indexing

- Validation rules

- Synchronization metadata

This provides a reliable persistence layer for analytics, AI retrieval, and future expansion.

# Section 12.2 — SQLAlchemy Models & Repository Implementation

> **Objective:** Implement the complete persistence layer using SQLAlchemy ORM, establish entity relationships, and build a reusable repository pattern that isolates database access from business logic.

---

# Overview

In Section 12.1, we designed the database schema.

In this section, we implement that design using **SQLAlchemy ORM**.

Instead of writing raw SQL throughout the application, every database operation will go through repositories.

Architecture:

```
FastAPI Route

↓

Service

↓

Repository

↓

SQLAlchemy ORM

↓

SQLite
```

This makes the code modular, testable, and easier to maintain.

---

# 12.2.1 Why SQLAlchemy ORM?

Instead of:

```sql
SELECT *
FROM questions
WHERE id = 56;
```

we can write:

```python
question = repository.get_by_id(56)
```

Benefits:

- Cleaner code
- Database abstraction
- Relationship management
- Easier migrations
- Type safety
- Better testing

---

# 12.2.2 Folder Structure

```
backend/

app/

├── database/

│   ├── base.py
│   ├── session.py
│   ├── models/
│   │      question.py
│   │      submission.py
│   │      tag.py
│   │      ai_note.py
│   │      sync.py
│   │
│   └── __init__.py
│
├── repositories/
│
│   ├── base_repository.py
│   ├── question_repository.py
│   ├── submission_repository.py
│   ├── tag_repository.py
│   ├── ai_repository.py
│   └── sync_repository.py
```

Each entity has its own model and repository.

---

# 12.2.3 ORM Model Responsibilities

Each model represents one table.

Example:

```
Question

↓

questions table
```

Responsibilities:

- Define columns
- Define relationships
- Apply constraints
- Provide metadata

Business logic should **not** be placed inside models.

Repositories isolate all database access.

Example:

```
Route

↓

QuestionService

↓
```

The service never knows how the data is stored.

A generic repository should provide reusable operations.

Typical methods:

```

update()

delete()

count()
```

- Find by slug
- Search by title
- Retrieve by difficulty
- Retrieve by tag
- Pagination

Example workflow:

```
Question ID

↓

Repository

↓

Question Object
```

# 12.2.9 Submission Repository

Responsibilities:

- Insert new submissions
- Retrieve latest submission
- Retrieve submissions by language
- Retrieve accepted submissions

- Get submission history

# 12.2.10 Tag Repository

Responsibilities:

# 12.2.12 Sync Repository

Responsibilities:

- Store last synchronization timestamp
- Store latest submission ID

# 12.2.13 Database Session Lifecycle

Each API request follows this pattern:

```
Incoming Request

↓

Create Session

↓

Repository Operations

↓

Commit / Rollback

↓

Close Session
```

This ensures that database connections are always released.

---

# 12.2.14 Transactions

Whenever multiple repositories participate in one operation:

```
Insert Question

↓

Insert Tags

↓

Insert Submission

↓

Commit
```

If an error occurs:

```
Rollback

↓

Database Restored
```

Atomic transactions prevent partial updates.

---

# 12.2.15 Exception Handling

Repositories should convert low-level database exceptions into meaningful application errors.

Examples:

| Database Error | Application Response |
|---------------|----------------------|
| Duplicate key | Question already exists |
| Foreign key failure | Invalid question reference |
| Connection failure | Database unavailable |

This prevents SQL-specific details from leaking to higher layers.

---

# 12.2.16 Pagination

Large result sets should support pagination.

Example:

```
Request

↓

Page = 2

Limit = 25

↓

Repository

↓

25 Records
```

This is useful for dashboards, APIs, and future multi-user support.

---

# 12.2.17 Filtering

Repositories should support filtering.

Examples:

```
Difficulty = Hard
```

```
Language = C++
```

```
Tag = Graph
```

```
Solved Between Two Dates
```

Filtering should happen in SQL rather than in Python for better performance.

# 12.2.18 Unit Testing

Every repository should have tests covering:

- Delete

- Pagination
- Error cases

Example test scenarios:

```

↓

```

```
Delete Question

↓

```

```

```

---

# 12.2.19 Repository Guidelines

Repositories should:

- Contain only persistence logic.
- Never call AI models.
- Never build prompts.
- Never perform analytics.
- Never contain business rules.

Those responsibilities belong to the service layer.

---

# 12.2.20 Benefits of This Design

This layered architecture provides:

- Strong separation of concerns.
- Easy testing using mock repositories.
- Database independence (SQLite → PostgreSQL migration later).
- Reusable CRUD logic.
- Clear ownership of responsibilities.

If the database changes in the future, only the repository layer needs modification.

- Modular
- Testable
- Scalable
- Database-agnostic
- Ready for analytics, scraping, and AI integration

Every future component—scraper, analytics engine, embedding pipeline, and AI agents—will interact with the database exclusively through these repositories.
