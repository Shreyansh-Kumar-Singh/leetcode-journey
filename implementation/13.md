# Section 13 — LeetCode Data Ingestion & Synchronization

> **Objective:** Build a reliable ingestion pipeline that imports the user's LeetCode question, submission, timestamp, language, runtime, memory, and solution information into SQLite while avoiding duplicate records.

---

## 13.1 Why This Layer Is Important

The entire AI/RAG system depends on the quality of the underlying data.

The pipeline is:

LeetCode
↓
Scraper / API Client
↓
Parser
↓
Validation
↓
SQLite
↓
Analytics
↓
Embeddings
↓
ChromaDB
↓
RAG
↓
LLM

Therefore, the scraper should be treated as a **data ingestion service**, not as part of the AI layer.

---

# 13.2 Important Security Rule

LeetCode authentication cookies are extremely sensitive.

Never:

- Commit cookies to GitHub.
- Put cookies in frontend JavaScript.
- Store cookies inside JSON files.
- Print cookies in logs.
- Send cookies to the LLM.
- Include cookies in screenshots or README files.

Store them only in environment variables or another secure secret store.

Example:

.env

LEETCODE_SESSION=...
CSRF_TOKEN=...

And:

.gitignore

.env

# 13.4 Why Use a Client Abstraction?

Do not put HTTP requests directly inside the synchronization logic.

Bad:

sync.py
    ↓
requests
    ↓
SQLite

Better:

sync.py
    ↓
LeetCodeClient
    ↓
Parser
    ↓
Repository

This makes the scraper easier to replace if LeetCode changes its API.

# 13.5 Client Responsibilities

The client handles:

- Authentication
- HTTP requests
- Request headers
- GraphQL/API communication
- Timeouts
- Retry behavior
- Response validation

The client should return raw data.

It should not directly write to SQLite.

---

# 13.6 Parser Responsibilities

The parser converts the external response into internal application objects.

Example:

External response:

{
    "id": "...",
    "title": "Two Sum",
    "statusDisplay": "Accepted",
    "lang": "cpp"
}

↓

Internal object:

SubmissionData(
    question_id=1,
    title="Two Sum",
    status="Accepted",
    language="cpp"
)

This prevents the rest of the application from depending on LeetCode's response format.

# 13.8 Accepted vs Failed Submissions

Do not automatically discard failed submissions.

Failed submissions can be extremely valuable for AI.

Example:

Accepted:

Two Sum

↓

Correct Solution

Failed:

Two Sum

↓

Wrong Answer

↓

Bug

The AI can later analyze:

- Common mistakes
- Number of attempts
- Time between failed and accepted attempts
- Repeated mistakes

Therefore, store submission history when possible.

---

# 13.9 Incremental Synchronization

Never download the complete submission history every time.

Instead:

SQLite

↓

Latest known submission timestamp

↓

Fetch newer records

↓

Insert only new submissions

This reduces:

- API requests
- Processing time
- Database writes
- Embedding costs

---

# 13.10 Synchronization Algorithm

Pseudo-code:

function sync():

    last_sync = get_last_sync()

    submissions = fetch_submissions_after(last_sync)

    for submission in submissions:

        if submission_exists(submission.id):

            continue

        parsed = parse(submission)

        validate(parsed)

        save(parsed)

    update_sync_timestamp()

---

# 13.11 Duplicate Prevention

The submission ID should be unique.

Database constraint:

UNIQUE(submission_id)

This provides a second layer of protection.

Even if the scraper accidentally downloads the same submission twice:

Existing submission
        ↓
Unique constraint
        ↓
Duplicate rejected

---

# 13.12 Synchronization Transaction

A single synchronization batch should ideally be transactional.

Example:

BEGIN

↓

Insert Questions

↓

Insert Tags

↓

Insert Submissions

↓

Update Sync Metadata

↓

COMMIT

If an unexpected database error occurs:

ROLLBACK

This prevents partially synchronized datasets.

---

# 13.13 Question Upsert

Questions may already exist.

Therefore:

Question exists?

YES
 ↓
Update metadata if necessary

NO
 ↓
Create question

This operation is called an **upsert**.

---

# 13.14 Tag Processing

For every question:

Question
 │
 ├── Array
 ├── Hash Table
 └── Sorting

The scraper should:

1. Find existing tags.
2. Create missing tags.
3. Create question-tag relationships.

Duplicate tags should never be created.

---

# 13.15 Source Code Handling

If source code is available, store it separately from basic submission metadata.

Possible architecture:

SQLite

↓

Submission Metadata

↓

Source Code

For larger datasets, source code can eventually be moved to files/object storage while SQLite stores the reference.

---

# 13.16 Data Normalization

External APIs may return inconsistent values.

For example:

C++

cpp

C++14

cpp14

These should be normalized.

Example:

normalize_language("C++")

↓

"cpp"

Similarly:

Accepted

accepted

Accepted

↓

"Accepted"

---

# 13.17 Timestamp Normalization

Always convert timestamps to a standard format.

Recommended:

UTC internally.

Example:

2026-08-22T15:30:00Z

The frontend can convert it to local time.

This prevents timezone-related analytics bugs.

---

# 13.18 Retry Strategy

Network requests can fail.

Use limited retries:

Request
 ↓
Failure
 ↓
Wait
 ↓
Retry
 ↓
Failure
 ↓
Retry
 ↓
Final Failure

Use exponential backoff.

Example:

Attempt 1
Wait 1 second

Attempt 2
Wait 2 seconds

Attempt 3
Wait 4 seconds

Do not retry indefinitely.

---

# 13.19 Rate Limiting

The scraper should behave conservatively.

Avoid:

- Very high request frequency.
- Parallel scraping of many endpoints.
- Unnecessary repeated requests.

Use:

Request
 ↓
Delay
 ↓
Request
 ↓
Delay

The goal is reliable synchronization, not maximum request speed.

---

# 13.20 Error Categories

Create separate error types.

AuthenticationError

↓

Invalid/expired credentials

NetworkError

↓

Connection failure

ParsingError

↓

Unexpected response format

DatabaseError

↓

SQLite failure

RateLimitError

↓

Too many requests

This makes error handling much easier.

# 13.26 What Happens After SQLite?

The scraper should NOT directly call the LLM.

Instead:

SQLite
   ↓
Detect changed records
   ↓
Embedding Pipeline
   ↓
ChromaDB

Then:

User Query
   ↓
Retriever
   ↓
ChromaDB
   ↓
LLM

This separation is extremely important.

---

# 13.27 Why SQLite Comes Before RAG

RAG should never directly depend on the external LeetCode service.

Correct:

LeetCode
 ↓
SQLite
 ↓
ChromaDB
 ↓
RAG

Not:

LeetCode
 ↓
RAG

SQLite gives us:

- Persistence
- Reproducibility
- Backup
- Data validation
- Analytics
- Ability to rebuild the vector database

---

# 13.28 Rebuilding ChromaDB

Suppose ChromaDB becomes corrupted.

We should not lose the project.

Simply:

SQLite
 ↓
Read all documents
 ↓
Generate embeddings
 ↓
Create ChromaDB again

Therefore:

SQLite = Source of Truth

ChromaDB = Derived Index

---

# 13.29 Testing Strategy

Test the scraper using mocked responses.

Do not repeatedly hit the real service during tests.

Test:

1. Successful response.
2. Empty response.
3. Authentication failure.
4. Network failure.
5. Rate limiting.
6. Malformed response.
7. Duplicate submission.
8. New submission.
9. Database failure.

# 13.31 Security Checklist

Before deploying:

- [ ] Cookies stored outside source code.
- [ ] `.env` ignored by Git.
- [ ] Cookies never logged.
- [ ] API keys never returned by API.
- [ ] Backend-only access to LeetCode credentials.
- [ ] HTTPS used in production.
- [ ] Rate limiting enabled.
- [ ] Authentication required for synchronization endpoints.

# Summary

The ingestion system provides a reliable bridge between LeetCode and the AI platform.

It provides:

- Secure credential handling
- Data normalization
- Incremental synchronization
- Duplicate prevention
- Transactional database updates
- Error handling
- Retry logic
- Rate limiting
- Sync monitoring
- RAG-ready data

Most importantly, SQLite remains the **single source of truth**, while ChromaDB remains a rebuildable semantic index.
