# Section 14 — Embedding Pipeline Implementation

> **Objective:** Convert LeetCode questions and solutions stored in SQLite into vector embeddings and store them in ChromaDB so the application can perform semantic retrieval.

---

# 14.1 What Are We Building?

Our current system is:
```
LeetCode
   ↓
SQLite
   ↓
Analytics / JSON
   ↓
GitHub Pages
```
We now add:
```
SQLite
   ↓
Document Builder
   ↓
Embedding Model
   ↓
ChromaDB
   ↓
Semantic Search
```
This is the first major component of the RAG system.

# 14.2 Why Embeddings?

Traditional search looks for matching words.

Example:

User asks:
```
"Show me problems where I need to combine overlapping ranges."
```
Keyword search may search for:
```
overlapping
ranges
```
But the database might contain:
```
Merge Intervals
Insert Interval
Meeting Rooms II
Non-overlapping Intervals
```
Semantic search can recognize that these problems are conceptually related.

# 14.3 Embedding Pipeline

The complete pipeline is:
```
SQLite
   │
   ▼
Fetch Questions/Submissions
   │
   ▼
Document Builder
   │
   ▼
Clean Text
   │
   ▼
Chunking
   │
   ▼
Embedding Model
   │
   ▼
Vector
   │
   ▼
ChromaDB
```
# 14.4 What Should Be Embedded?

Do not blindly embed every database column.

The embedding should contain information that is useful for semantic retrieval.

For each problem, consider:
```
Problem Title

Problem Description

Tags

Difficulty

Solution Approach

Source Code

Complexity

Submission Information
```

Example document:
```

Problem: Merge Intervals

Difficulty: Medium

Tags:
Array, Sorting, Intervals

Approach:
Sort intervals by starting position and merge overlapping intervals.

Complexity:
Time: O(n log n)
Space: O(n)
```
# 14.5 Metadata vs Embedded Text

Not everything should go into the embedding.

Separate:
```

Semantic Content
```
from:
```
Structured Metadata
```
Example:
```
Document

↓

"Merge intervals by sorting..."
```
Metadata:
```
{
    "question_id": 56,
    "difficulty": "Medium",
    "language": "cpp",
    "tags": "Array,Sorting"
}
```
This distinction is important.

# 14.6 Why Metadata Matters

Suppose the user asks:
```
"Give me hard Graph problems solved in C++."

Semantic similarity alone is not enough.
```
We need:
```
Semantic Search
+
Metadata Filtering
```
Workflow:
```
Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Metadata Filter
 ↓
Top Results
```
#14.7 ChromaDB Document Structure

Each ChromaDB record should contain:
```
ID

Document

Embedding

Metadata
```
Example:
```
ID:
question_56_solution_123456

Document:
"Merge intervals by sorting..."

Metadata:
{
    question_id: 56,
    submission_id: 123456,
    difficulty: "Medium",
    language: "cpp",
    tags: "Array,Sorting",
    timestamp: "2026-08-20T10:30:00"
}
```
# 14.8 Document IDs

IDs must be deterministic.

Recommended:
```
question_{question_id}_submission_{submission_id}
```
Example:
```
question_56_submission_123456
```
Benefits:

- Duplicate prevention
- Easy updates
- Easy deletion
- Easy debugging

# 14.9 Embedding Version

Embedding models can change.

For example:
```
Model V1

↓

Model V2
```
The generated vectors may no longer be compatible.

Therefore store:
```
embedding_model

embedding_version
```
Example:
```
{
    "embedding_model": "all-MiniLM-L6-v2",
    "embedding_version": "1"
} 
```
# 14.10 Choosing the Embedding Model

For the first implementation, use a lightweight Sentence Transformer.

Example:
```
all-MiniLM-L6-v2
```
Advantages:

- Small
- Fast
- Runs locally
- No embedding API cost
- Good for a portfolio project

Later you can evaluate larger embedding models.

```
pip install sentence-transformers
```

- **sync.py** — Synchronize SQLite and ChromaDB.


# 14.13 Loading the Model

The model should be loaded only once.

Bad:
```
Every Request
    ↓
Load Model
    ↓
Generate Embedding
```
This is extremely slow.

Correct:
```
Application Startup
       ↓
Load Model Once
       ↓
Reuse Model
```
This is called model caching.

# 14.14 Document Builder

The document builder converts structured database data into searchable text.

Example:
```
Question:

Merge Intervals

Difficulty:

Medium

Tags:

Array, Sorting

Solution:

Sort intervals and merge overlapping ranges.

Complexity:

O(n log n)
```
This becomes the input to the embedding model.

# 14.15 Source Code Embedding

Should source code be embedded?

Yes, but carefully.

A solution can be represented as:
```
Problem
+
Approach
+
Code
```
However, very large source files should not be blindly embedded as one document.

**Instead:**
```
Problem Description
        │
        ├── Approach
        │
        ├── Complexity
        │
        └── Source Code
```
These can become separate chunks.

# 14.16 Chunking Strategy

For this project, do not use arbitrary chunking first.

LeetCode solutions are naturally structured.

Use semantic sections.

Example:
```
Chunk 1

Problem Metadata

Chunk 2

Solution Explanation

Chunk 3

Source Code

Chunk 4

Complexity Analysis
```
This is better than blindly splitting every 500 characters.

# 14.17 Chunk IDs

Use deterministic chunk IDs.

Example:
```
56_123456_metadata

56_123456_explanation

56_123456_code

56_123456_complexity
```
This allows individual chunks to be updated.

# 14.18 Example Document
```
Problem:
Two Sum

Difficulty:
Easy

Tags:
Array, Hash Table

Approach:
Use a hash map to store previously seen values and
check whether target - current value exists.

Complexity:
Time O(n)
Space O(n)
```
Embedding:
```
[0.021, -0.314, 0.102, ...]
```
The vector may contain hundreds of dimensions depending on the model.

#14.19 Batch Embedding

Do not generate one embedding at a time for thousands of documents.

Instead:
```
Documents

↓

Batch 1

↓

Batch 2

↓

Batch 3

↓

...
```
Example:
```
batch_size = 32
```
Batch processing improves throughput.

# 14.20 Initial Indexing

When the system is run for the first time:
```
SQLite

↓

Read All Records

↓

Build Documents

↓

Generate Embeddings

↓

Insert into ChromaDB
```
Example:
```
SQLite:
1,000 submissions

↓

1,000–4,000 chunks

↓

ChromaDB
```
The exact number depends on the chunking strategy.

# 14.21 Incremental Indexing

After the initial indexing, do not regenerate everything.

Workflow:
```
SQLite

↓

Find New/Modified Records

↓

Build Documents

↓

Generate Embeddings

↓

Upsert into ChromaDB
```
This saves:
- CPU
- Time
- Memory
- API cost

# 14.22 Detecting Changes

Store a content hash.

Example:
```
SHA-256(
    problem +
    solution +
    code
)
```
Save:
```
content_hash
```
Next synchronization:
```
Current Hash
     │
     ▼
Compare
     │
 ┌───┴───┐
 │       │
Same   Changed
 │       │
Skip    Re-embed
```
# 14.23 Why Hashing Is Useful

Suppose the same solution is synchronized every day.

Without hashing:
```
Same solution
     ↓
Generate embedding
     ↓
Waste resources
```
With hashing:
```
Same content
     ↓
Hash unchanged
     ↓
Skip
```
# 14.24 ChromaDB Upsert

Use deterministic IDs with upsert semantics.

Conceptually:
```
ID exists?

YES
 ↓
Update

NO
 ↓
Insert
```
This prevents duplicate vectors.

# 14.28 Similarity Score

ChromaDB returns similarity information.

Conceptually:
```
Query

    ↓

Similarity

    ↓

0.92  Merge Intervals

0.87  Insert Interval

0.81  Meeting Rooms II

0.72  Two Sum
```
Higher similarity generally means stronger semantic relevance, but the exact score interpretation depends on the distance metric and configuration.

Do not blindly treat a score as a probability.

# 14.29 Top-K Retrieval

The retriever should not return the entire database.

Use:
```
Top K = 5
```
Example:
```
Query
 ↓
ChromaDB
 ↓
Top 5 documents
```
Later, reranking can improve results.

# 14.31 Rebuild Operation

A very important administrative operation:
```
POST /api/rag/rebuild
```
Workflow:
```
Delete ChromaDB Collection

↓

Read SQLite

↓

Build Documents

↓

Generate Embeddings

↓

Insert Everything

↓

Verify Count
```
Because SQLite is the source of truth, the vector index can always be reconstructed.

# 14.32 Embedding Health Check

```
GET /api/rag/status
```
Example response:
```
{
    "collection": "leetcode_solutions",
    "sqlite_documents": 1200,
    "vector_documents": 1200,
    "embedding_model": "all-MiniLM-L6-v2",
    "status": "healthy"

```
This helps detect synchronization problems.

# 4.33 Embedding Failure Handling

If an embedding fails:
```
SQLite
   ↓
Record Exists
   ↓
Embedding Failed
   ↓
Retry Later
```
Do not delete the original database record.

The database and vector index must remain independent.

# 14.34 Embedding Queue

For larger datasets, use a queue:
```
SQLite
   ↓
Pending Documents
   ↓
Embedding Worker
   ↓
ChromaDB
```
The queue can be implemented later using:
- BackgroundTasks
- APScheduler
- Celery
- Redis Queue

For the first version, a simple background worker is sufficient.

# 14.36 What Should NOT Be Embedded?

Avoid embedding irrelevant information such as:
```
submission database IDs

internal database timestamps

GitHub deployment metadata

authentication information

API keys

cookies
```
Only information useful for semantic reasoning should be embedded.

# 14.37 Privacy & Security

Never embed:
```
LEETCODE_SESSION

CSRF_TOKEN

GITHUB_TOKEN

GEMINI_API_KEY
```
Never send authentication credentials to the LLM.

The embedding database should contain only application data required for retrieval.

# 14.39 Performance Considerations

For a personal LeetCode dataset, local embeddings are usually sufficient.

Important optimizations:
- Load model once.
- Batch documents.
- Use incremental indexing.
- Hash content.
- Avoid unnecessary re-embedding.
- Keep metadata small.
- Use top-K retrieval.

# 14.41 Important Design Decision

The most important architectural rule in this section is:
```
SQLite = Source of Truth

ChromaDB = Derived Semantic Index
```
Never make ChromaDB the only place where your application data exists.

If the vector database is deleted:
```
SQLite
   ↓
Rebuild
   ↓
ChromaDB
```
The system recovers without losing data.
