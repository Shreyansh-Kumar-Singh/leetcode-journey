# Section 16 — Building the RAG Pipeline

> **Objective:** Learn how Retrieval-Augmented Generation (RAG) works and implement a complete RAG pipeline for your LeetCode AI Assistant. After this section, the AI will answer questions using **your own LeetCode data** instead of relying only on the LLM's pretrained knowledge.

---

# 16.1 What is RAG?

RAG stands for:

```
Retrieval

Augmented

Generation
```

Instead of asking the LLM to answer only from its training data, we first retrieve relevant information from our own database and provide it as context.

---

# 16.2 Why Do We Need RAG?

Suppose you ask:

```
How many Graph problems have I solved?
```

An LLM has no idea.

It doesn't know:

- Your LeetCode history
- Your SQLite database
- Your GitHub repository
- Your solved problems

Without RAG:

```
Question

↓

LLM

↓

Guess (Hallucination)
```

With RAG:

```
Question

↓

Retrieve User Data

↓

LLM

↓

Grounded Answer
```

# 16.6 Components of RAG

Every RAG system has four major parts:

```
Documents

↓

Embeddings

↓

Retriever

↓

```

# 16.7 Step 1 — Documents

Your documents are **not PDFs**.

Instead, every LeetCode problem becomes a document.

Example:

```text
Title:
Two Sum

Difficulty:
Easy

Tags:
Array, Hash Map

Solution:
...

Submission Date:
...
```

Each problem is a searchable document.

---

# 16.8 What Should Be Indexed?

For your project, index:

```
Problem Title

Problem Description

Difficulty

Tags

Your Solution

Language

Submission Time

Complexity

Notes (optional)
```

The richer the document, the better retrieval quality.

```json
      "Binary Search"
  ],

  "solution": "...",

  "language": "C++"

```

---

# 16.10 Step 2 — Embeddings

The LLM cannot search plain text efficiently.

Instead:

```
Text

↓

Embedding Model

↓

Vector
```

Example:

```
"Binary Search"

↓

[0.14, -0.82, 0.43, ...]
```

This numerical representation captures semantic meaning.

---

# 16.11 What is an Embedding?

An embedding is a dense numerical representation of text.

Texts with similar meanings produce vectors that are close together.

Example:

```
Binary Search

↓

Vector A
```

```
Search in Sorted Array

↓

Vector B
```

A and B are close in vector space.

---

# 16.12 Why Embeddings?

Traditional search:

```
Exact Words
```

Embedding search:

```
Meaning
```

Example:

User asks:

```
Find problems about shortest path.
```

Even if the document never contains the phrase "shortest path," the retriever can still find Dijkstra or BFS-related problems.

---

# 16.13 Step 3 — Vector Database

Embeddings must be stored somewhere.

Options include:

```
ChromaDB

FAISS

Pinecone

Weaviate

Milvus
```

For this project, we'll use **ChromaDB** because it is lightweight and easy to integrate locally.

# 16.14 Step 4 — Retriever

The retriever performs:

```
User Query

↓

Embedding

↓

Similarity Search

↓

Top K Documents
```

It never generates answers—it only retrieves relevant context.

# 16.19 Chunking

Large documents should not be embedded as one block.

Instead:

```
Large Document

↓

Chunk 1

Chunk 2

Chunk 3

...
```

Smaller chunks improve retrieval accuracy.

---

# 16.20 Chunk Size

For code and LeetCode problems:

```
300–800 tokens
```

is often a good starting point.

Too small:

```
Context lost
```

Too large:

```
Poor retrieval precision
```

---

# 16.21 Chunk Metadata

Every chunk should store metadata.

Example:

```json
{
  "problem": "Two Sum",
  "difficulty": "Easy",
  "tags": ["Array", "Hash Map"],
  "language": "C++"
}
```

Metadata enables filtering later.

---

# 16.22 Similarity Search

Suppose the user asks:

```
Sliding Window
```

The retriever computes:

```
Query Embedding

↓

Compare

↓

All Stored Embeddings

↓

Similarity Score

↓

Top K
```

The most similar chunks are returned.

---

# 16.23 Top-K Retrieval

Typically retrieve:

```
Top 3

Top 5

Top 10
```

Retrieving too many chunks may reduce answer quality by adding irrelevant context.

---

# 16.24 Grounding

The LLM should answer **only** using retrieved information whenever possible.

Bad:

```
LLM invents data.
```

Good:

```
Retriever provides facts.

↓

LLM explains facts.
```

Grounding is one of the biggest advantages of RAG.

---

# 16.25 Preventing Hallucinations

System Prompt:

```
Answer only using the retrieved context.

If the answer is unavailable,

say that you do not have enough information.
```

This reduces fabricated responses.

---

# 16.26 Retriever vs Generator

Retriever:

```
Searches
```

Generator:

```
Explains
```

Keep these responsibilities separate.

---
