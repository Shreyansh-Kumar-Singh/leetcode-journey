# Section 18 — Retrieval Pipeline & Query Processing

> **Objective:** Build the complete retrieval engine that sits between the user's question and the LLM. This component is responsible for understanding the query, retrieving relevant information from SQLite and ChromaDB, ranking the results, and constructing high-quality context for the LLM.

---

# 18.1 Why Retrieval Matters

The LLM is only as good as the context you provide.

Poor retrieval:

```text
Question

↓

Irrelevant Documents

↓

Wrong Answer
```

Good retrieval:

```text
Question

↓

Relevant Documents

↓

Accurate Answer
```

Most RAG systems fail because of poor retrieval—not because of the LLM.

---

The complete retrieval workflow:

```text
User Question
      │
      ▼

      │
      ▼

      │
      ▼

      │
      ▼

      │
      ▼

      │
      ▼

      │
      ▼

```

---

# 18.3 Responsibilities

The retrieval engine should:

```
Understand Query

Generate Embedding

Search Vector DB

Filter Results

Rank Results

Build Context

Return Documents
```

It should **never generate the final answer**.

---

# 18.4 Query Types

Your assistant will receive many types of questions.

Examples:

```
Explain my solution.

Recommend problems.

Find similar questions.

Show Graph problems.

How many DP problems?

What should I revise?

Weak topics?
```

Each type may require a different retrieval strategy.

---

# 18.5 Intent Classification

Before retrieval, determine the intent.

Example:

| User Query | Intent |
|------------|--------|
| Explain my Two Sum solution | Solution Explanation |
| Recommend Graph problems | Recommendation |
| Weak topics | Analytics |
| Similar to Merge Intervals | Semantic Search |

Intent classification helps choose the correct tools.

---

# 18.6 Query Normalization

Normalize user input before searching.

Example:

```
graphs

↓

graph
```

```
binary-search

↓

binary search
```

This improves retrieval consistency.

---

# 18.7 Query Embedding

After preprocessing:

```text
Question

↓

Embedding Model

↓

Query Vector
```

This vector will be compared with stored document vectors.

---

# 18.8 Semantic Search

Pipeline:

```text
Query Vector

↓

ChromaDB

↓

Similarity Scores

↓

Top-K Documents
```

This retrieves documents with similar meaning, not just matching keywords.

---

# 18.9 Choosing K

Example:

```
Top 3

Top 5

Top 10
```

Typical values:

- Small questions → Top 3
- Recommendations → Top 5
- Complex explanations → Top 8–10

Too many documents can overwhelm the LLM.

---

# 18.10 Similarity Scores

Example:

| Problem | Score |
|----------|------:|
| Number of Islands | 0.96 |
| Clone Graph | 0.94 |
| Course Schedule | 0.91 |
| Word Ladder | 0.82 |

Higher similarity indicates stronger relevance.

---

# 18.11 Similarity Threshold

Don't return every match.

Example threshold:

```
Similarity ≥ 0.75
```

Anything below may be ignored to reduce noise.

---

# 18.12 Metadata Filtering

Suppose the user asks:

```
Hard Graph problems
```

Pipeline:

```text
Semantic Search

↓

Filter

Difficulty = Hard

↓

Return Results
```

Filtering combines structured metadata with semantic search.

---

# 18.13 Hybrid Retrieval

Instead of relying only on embeddings:

```text
Keyword Search

+

Semantic Search

↓

Merge

↓

Rank
```

Hybrid retrieval often performs better than either approach alone.

---

# 18.14 SQL + Vector Search

Some questions require SQL instead of embeddings.

Example:

```
How many Medium problems have I solved?
```

SQL is the correct tool.

Semantic search is unnecessary.

Your AI Agent should decide which retrieval method to use.

---

# 18.15 Retrieval Decision Tree

```text
Question
     │
     ▼
Analytics?
 ┌───────┴────────┐
Yes              No
 │                │
 ▼                ▼
SQL         Semantic Search
```

The retriever should avoid unnecessary vector searches.

---

# 18.16 Context Selection

Suppose Top-10 documents are returned.

Should all 10 go into the prompt?

Usually no.

Instead:

```
Top 10

↓

Select Best 5

↓

Prompt
```

This keeps prompts focused and reduces token usage.

---

# 18.17 Context Ordering

Arrange documents logically.

Example:

```
Most Relevant

↓

Supporting Documents

↓

Additional Context
```

The order can influence the LLM's output.

---

# 18.18 Removing Duplicates

Sometimes similar chunks are retrieved.

Instead of:

```
Two Sum

Two Sum

Two Sum
```

Keep only one.

This maximizes useful context.

---

# 18.19 Query Expansion

User asks:

```
BFS
```

Expand internally:

```
Breadth First Search

Graph Traversal

Queue
```

Query expansion can improve recall without changing the user's request.

---

# 18.20 Context Builder

The context builder combines retrieved documents into a structured prompt.

Example:

```text
Document 1

------------

Document 2

------------

Document 3
```

This final context is passed to the LLM.

---

# 18.21 Maximum Context Size

Every model has a context limit.

If retrieved content exceeds the limit:

```
Rank

↓

Trim

↓

Send
```

Avoid blindly sending every retrieved document.

---

# 18.22 Retrieval Cache

Frequently repeated questions:

```
Weak topics

Today's recommendations

Total solved
```

can be cached.

Benefits:

```
Lower Latency

Lower Cost

Reduced Database Load
```

---

# 18.23 No Results Found

Sometimes retrieval returns nothing.

Example:

```
Similarity < Threshold
```

Instead of inventing an answer:

```
No relevant documents found.

Please rephrase your question.
```

This is preferable to hallucination.

---

# 18.24 Multi-Step Retrieval

Complex questions may require several retrieval steps.

Example:

```
Recommend Graph problems

↓

Find Weak Graph Topics

↓

Retrieve Similar Problems

↓

Generate Plan
```

This forms the basis for AI agents.

---

These metrics help improve retrieval quality over time.
