# Section 4 — Database Design & Data Model

---

# Overview

The current SQLite database is sufficient for analytics, but not for AI.

For Retrieval-Augmented Generation (RAG), the system needs additional metadata and a vector database that stores semantic representations (embeddings) of the user's coding history.

**Design Principle**

SQLite remains the **single source of truth**.

The vector database is a **derived index** built from SQLite.

```
           LeetCode
               │
               ▼
        SQLite Database
               │
               ├──────────────┐
               ▼              ▼
        JSON Generator   Embedding Pipeline
               │              │
               ▼              ▼
        Static Website    ChromaDB
```

---

# 4.1 Why Keep SQLite?

Many beginners try to replace SQLite with a vector database.

This is not recommended.

**SQLite is best for:**

- Exact lookups
- Filtering
- Aggregation
- Updates
- Relationships
- Historical records

**Vector Database is best for:**

- Semantic search
- Similarity search
- Natural language retrieval

Use both together.

# 4.6 What Should Be Embedded?

Do **not** embed only the title.

Instead, combine meaningful fields.

Recommended text:

```
Question Title

Difficulty

Tags

Problem Description

My Solution

Complexity

Notes
```

Example

```
Title:
Merge Intervals

Difficulty:
Medium

Tags:
Array
Sorting

Problem:
Given an array of intervals...

My Solution:
Sort intervals...
```

This produces richer embeddings.

# 4.7 Metadata Stored with Each Embedding

Every embedding should include metadata.

Example

```json
{
  "question_id": 56,
  "title": "Merge Intervals",
  "difficulty": "Medium",
  "language": "C++",
  "tags": [
    "Array",
    "Sorting"
  ],
  "submitted_at": "2026-08-10",

  "leetcode_url": "https://leetcode.com/problems/merge-intervals/",
```

Metadata enables filtering without recomputing embeddings.

# 4.9 Synchronization Strategy

The vector database should never be edited manually.

SQLite is always the master.

```
New Submission

↓

SQLite Updated

↓

Check Changes

↓

Generate Embedding

↓

Insert Into ChromaDB
```

---

# 4.10 Update Workflow

```
Run Scraper

↓

Download New Submission

↓

SQLite

↓

Has Question Changed?

↓

YES

↓

Generate Embedding

↓

Update ChromaDB
```

If nothing changed

```
Skip Embedding
```

This saves time and API costs.

# 4.15 Why This Design?

This architecture follows a common production pattern used in modern AI systems:

- **SQLite** handles transactional and analytical data.
- **ChromaDB** acts as a semantic search index.
- The **embedding pipeline** keeps both synchronized automatically.
- If ChromaDB is lost or corrupted, it can be fully regenerated from SQLite.
- Future embedding models can be adopted without changing the core database.

This separation keeps the system reliable, scalable, and easy to maintain.
