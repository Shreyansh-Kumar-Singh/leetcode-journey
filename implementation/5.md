# Section 5 — Embedding Pipeline & Vector Database

---

# Overview

The Embedding Pipeline is the heart of the Retrieval-Augmented Generation (RAG) system.

Its responsibility is to transform your LeetCode data into semantic vectors that can be searched efficiently.

Without embeddings, the AI can only perform keyword matching.

With embeddings, the AI understands the **meaning** of questions, solutions, and algorithms.

---

# 5.1 What is an Embedding?

An embedding is a dense numerical representation of text.

Instead of storing text as words, an embedding model converts it into a vector.

Example

```
Question

↓

"Merge Intervals"

↓

Embedding Model

↓

[0.23, -0.81, 0.52, ...]
```

Two documents discussing similar algorithms will have vectors that are close together.

---

# 5.2 Why Embeddings?

Traditional search:

```
Search:
Graph
```

Returns only titles containing "Graph".

Semantic search:

```
Search:
Questions using BFS
```

Returns

- Clone Graph
- Number of Islands
- Course Schedule
- Rotting Oranges

Even if the word "BFS" never appears in the title.

---

# 5.3 Embedding Pipeline Architecture

```
SQLite
```

Every new submission passes through this pipeline.

# 5.7 Designing the Embedding Document

Do **not** embed only the question title.

Instead, create a rich document.

Example:

```
Title:
Merge Intervals

Difficulty:
Medium

Tags:
Array
Sorting

Problem Description:
Given an array of intervals...

My Solution:
Sort intervals by start time...

Time Complexity:
O(n log n)

Space Complexity:
O(1)

Submission Date:
2026-08-10
```

The more meaningful context included, the better the retrieval quality.

---

# 5.8 Document Builder

The first step is to convert database records into documents.

Input:

```
SQLite Row
```

Output:

```
Plain Text Document
```

Example Python:

```python
def build_document(question):
    return f"""
Title: {question.title}

Difficulty: {question.difficulty}

Tags:
{", ".join(question.tags)}

Problem:
{question.description}

Solution:
{question.solution}

Complexity:
Time: {question.time_complexity}

Space: {question.space_complexity}
"""
```

This document is sent to the embedding model.

---

# 5.9 Generating Embeddings

Example:

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer(
    "all-MiniLM-L6-v2"
)

embedding = model.encode(document)
```

Result:

```
384-dimensional vector
```

Store this vector in ChromaDB.

---

# 5.10 Initializing ChromaDB

Example:

```python
import chromadb

client = chromadb.PersistentClient(
    path="./vector_db"
)

collection = client.get_or_create_collection(
    "leetcode_submissions"
)
```

Now the vector database is ready.

---

# 5.11 Storing Documents

For every solved problem:

```
Question

↓

Embedding

↓

Metadata

↓

ChromaDB
```

Example:

```python
collection.add(
    ids=["56"],
    documents=[document],
    embeddings=[embedding],
    metadatas=[metadata]
)
```

---

# 5.12 Metadata Design

Each embedding should include metadata.

Example:

```python
metadata = {
    "question_id": 56,
    "difficulty": "Medium",
    "language": "C++",
    "tags": "Array,Sorting",
    "timestamp": "2026-08-10"
}
```

Metadata allows filtering before retrieval.

Example:

```
Only Hard Questions

AND

Language = C++
```

---

# 5.13 Incremental Updates

Do **not** regenerate all embeddings every time.

Instead:

```
Run Scraper

↓

Find New Questions

↓

Generate Embeddings

↓

Insert Only New Documents
```

Benefits:

- Faster
- Lower CPU usage
- Better scalability

---

# 5.14 Updating Existing Questions

If the solution changes:

```
Delete Old Vector

↓

Generate New Embedding

↓

Insert Updated Vector
```

This keeps the vector database synchronized with SQLite.

---

# 5.15 Similarity Search

When a user asks:

```
Questions similar to Merge Intervals
```

Workflow:

```
Question

↓

Embedding Model

↓

Query Vector

↓

ChromaDB

↓

Top 5 Matches
```

Example:

```python
results = collection.query(
    query_embeddings=[query_embedding],
    n_results=5
)
```

---

# 5.16 Choosing Similarity Metric

Common metrics:

| Metric | Recommended |
|----------|-------------|
| Cosine Similarity | ✅ |
| Euclidean Distance | Sometimes |
| Dot Product | Large Models |

Recommendation:

```
Cosine Similarity
```

Reason:

Sentence-transformer models are optimized for cosine similarity.

# 5.17 Top-K Retrieval

Typical values:

| K | Use Case |
|---|----------|
| 3 | Quick answers |
| 5 | Recommended |
| 10 | Detailed analysis |

For this project:

```
Top-K = 5
```

provides a good balance between relevance and context size.

# 5.19 Performance Considerations

As the number of solved problems grows:

- Cache the embedding model (load once).
- Batch embedding generation.
- Avoid duplicate embeddings.
- Use persistent ChromaDB storage.
- Index metadata for filtering.
- Regenerate embeddings only when content changes.

Even with several thousand problems, this approach performs efficiently on a typical laptop.

---

# 5.20 Future Improvements

The embedding pipeline can later be enhanced by:

- Generating separate embeddings for:
  - Problem statement
  - User solution
  - AI summary
- Supporting multiple embedding models.
- Re-ranking retrieved results using a cross-encoder.
- Hybrid search (keyword + vector search).
- Automatic embedding regeneration when switching models.

These enhancements can improve retrieval quality without changing the overall architecture.
